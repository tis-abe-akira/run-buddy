# ADR-0007: 永続化ライブラリの選定（PostgreSQL + RLS）

- ステータス: Accepted（2026-10-31 承認。jOOQ を採用）
- 追記: 2026-10-31 に Spring の `JdbcClient`（ORMを使わない素のSQL）も同じ条件で比較した
- 日付: 2026-10-31

## コンテキスト

Phase 1 のデータはメモリ上にしかない（`InMemoryMonthlyPlanRepository`、`InMemoryRunResultRepository`）。
これを PostgreSQL に保存するようにする。将来は Row Level Security（RLS）で、ユーザーごとにデータを分けたい。

ライブラリを選ぶうえで、このプロジェクトならではの前提は次の4つ。

1. **ドメインモデルはイミュータブルな record で、不変条件をコンストラクタで守っている**（`MonthlyPlan`、`RunResult`、値オブジェクトの `Distance`）。永続化のためにドメインを書き換える（可変にする、引数なしコンストラクタを足す）ことは避けたい。
2. **リポジトリはすでにポートになっている**（ADR-0004）。どのライブラリを選んでも、変わるのはアダプタだけ。
3. **PostgreSQL 特有の機能を使う**: RLS（`set_config` でセッション変数を設定）、`INSERT ... ON CONFLICT`（取り込みを何度実行しても重複させないため）。
4. **コードの多くを AI エージェントが書く**: SQL やマッピングの誤りを、実行時ではなくコンパイル時に見つけられる方が安全。

### RLS をアプリから使う方法（どのライブラリでも共通）

- トランザクションの最初に `select set_config('app.user_id', ?, true)` を実行する（第3引数が `true` なので、トランザクションが終われば消える。コネクションプールで別のリクエストに値が残らない）。
- アプリは**テーブルの所有者ではないロール**で接続する（所有者は RLS を素通りするため）。マイグレーション（Flyway）は所有者ロールで実行する。
- これは Spring のトランザクション管理に乗るどのライブラリでも、同じ仕組み（トランザクション開始時に呼ぶ小さな部品）で実装できる。違いが出るのは「ライブラリの裏で何が起きるか」が読みやすいかどうか。

### 各案を一言で

- **JPA**: エコシステムは最大。ただ、このプロジェクトの前提1（record のドメイン）と前提4（挙動の見通し）に合わず、ドメインと JPA エンティティの二重管理になる。RLS を「試す」目的にも、裏で発行されるSQLが見えにくい点が邪魔になる。
- **MyBatis**: SQLを完全に制御できて堅実。ただ、マッピングの誤りが実行時まで分からないので、AI が書くとテストでしか守れない。
- **Spring Data JDBC**: DDD の集約の考え方が `MonthlyPlan`（親）＋`PlannedWorkout`（子のリスト）にそのまま当てはまる。一方で、取り込みの upsert や集計クエリは生SQLを書くことになり、そこでは型安全性がない。
- **jOOQ**: PostgreSQL の機能と RLS の検証に一番素直。スキーマから生成したコードのおかげで、AI が書いたクエリの誤りをコンパイラが見つけられる。代わりにコード生成の仕組みが必要になる（下記）。
- **Doma**: 2-way SQL とコンパイル時検査のバランスが良い。ただ、利用者と情報が比較的少ない。

### jOOQ のコード生成について

コード生成には DB のスキーマが必要になる。方法は2つある。

- (a) ビルド中に Testcontainers で PostgreSQL を起動し、Flyway を流してからコードを生成する。本物の PostgreSQL のスキーマから作れる。
- (b) jOOQ の `DDLDatabase` で、Flyway のSQLファイルを解析して生成する。DB は要らないが、RLS のポリシー定義などは解析を除外する指定が必要になる。

スパイクでは、(a) の考え方をスクリプトで実現した（`backend/scripts/generate-jooq.sh`）。スクリプトが使い捨ての PostgreSQL コンテナを起動し、Flyway と jOOQ のコード生成を流す。生成したコードはコミットするので、通常のビルドに Docker は要らない。`testcontainers-jooq-codegen-maven-plugin` も検討したが、0.0.4 と古く、Boot 4 が管理するバージョンとの互換性が不安なので見送った。

## 推奨

**第一候補は jOOQ、次点は Spring Data JDBC。** どちらにするかは、両方で小さく作ってみて（スパイク）から決める。

決め方の案は次のとおり。

1. Flyway で `monthly_plan` / `planned_workout` / `run_result` テーブルを作る。
2. **リポジトリの契約テスト**（抽象テストクラス）を書き、`InMemory` 実装・jOOQ 実装・Spring Data JDBC 実装の3つに同じテストを流す。
   - 例: 保存したものを読み戻せる / ワークアウトが日付順になる / 取り込みを何度実行しても重複しない
3. 比べる観点:
   - アダプタのコード量
   - upsert の書きやすさ
   - RLS（`set_config`）を入れたときに読みやすいか
   - AI エージェントが間違えたときに、どの段階で気付けるか（コンパイル時／起動時／テスト実行時）
4. 結果をこの ADR に追記し、Accepted にする。

JPA と MyBatis は、この表の時点で候補から外す（理由は上の「各案を一言で」）。

## 結果（トレードオフ）

- どれを選んでも、ドメインとサービスは変わらない（ポートを分けておいた効果）。
- jOOQ を選んだ場合は、ビルドとCIにコード生成の手順が増える。
- RLS は「アプリが所有者ではないロールで接続する」ことが前提なので、DB のロール設計（マイグレーション用とアプリ用）を別の ADR で決める。

## スパイクの結果（2026-10-31）

### 作ったもの

- **スキーマ:** Flyway の `V1__create_plans_and_runs.sql`。RLS のポリシー、`user_id` 列の既定値、関数 `app_current_user_id()` を含む。
- **アダプタ:** 次の3つ。`runbuddy.persistence=jooq|jdbc|jdbcclient` で切り替える（DB を使わない `memory` もある）。
  - jOOQ 版（`persistence/jooq`）
  - Spring Data JDBC 版（`persistence/jdbc`）
  - **Spring の `JdbcClient` 版（`persistence/jdbcclient`）:** ORM を使わず、素のSQLを文字列で書く。比較の基準にした。
- **RLS の仕組み:** `RlsTransactionManager` がトランザクションの開始時に `set_config('app.user_id', ?, true)` を実行する。3つのライブラリで共通（24行）。
- **契約テスト:** プラン5件・ラン7件・RLS 2件・HTTP 経由の結合テスト2件。InMemory と3つのアダプタに同じテストを流し、**すべて一度で通った**（全体で95件）。DB を使うテストは Testcontainers（PostgreSQL 17）で、本番と同じく所有者ではないロールで接続する。テストごとに新しいユーザーとして実行するので、後片付けは要らない。

### 計測 1: 間違いにどの段階で気付けるか

コードにわざと誤りを入れて確かめた。

| 入れた誤り | jOOQ | Spring Data JDBC | JdbcClient |
|---|---|---|---|
| カラム名の打ち間違い | **コンパイルエラー** | テスト時（9件エラー） | テスト時（9件エラー） |
| 型の違う値の並び順を取り違える | **コンパイルエラー** | 該当しない（名前で対応付ける） | 該当しない（名前付きパラメータ） |
| パラメータ名の打ち間違い（`:distanceMeter`） | 該当しない | 該当しない | テスト時（9件エラー） |
| カラムを違う Java の型で読む（timestamp を LocalDate で読む） | **コンパイルエラー**（`Field<LocalDateTime>` に型が付いている） | テスト時 | テスト時（4件失敗。時刻が落ちる） |
| 同じ型（long 同士）の値を入れ替える | テスト時（4件失敗） | テスト時（4件失敗） | テスト時（4件失敗） |
| スキーマを変えたのにコードを直し忘れる | コード生成をやり直すとコンパイルエラー | テスト時 | テスト時 |

気付くまでの時間（この環境での目安）: コンパイル 約5秒。DB を使うテストを1アダプタ分（コンテナの起動を含む）流すと 約12秒。差は数倍程度だが、**DB を使うテストは Docker がないと動かない**（この開発環境でも、最初は Docker デーモンが止まっていた）。コンパイルはどこでも必ず動く。

### 計測 2: 発行されるSQLの本数

PostgreSQL の `log_statement=all` で数えた。BEGIN / COMMIT / set_config は除く。

| 操作 | jOOQ | Spring Data JDBC | JdbcClient |
|---|---|---|---|
| 24件のランを取り込む（新規） | **2** | 25 | 25（※） |
| 同じ24件を再度取り込む | **2** | 25 | 25（※） |
| 22件のワークアウトを含むプランを保存 | **3** | 24〜25 | 24（※） |
| プランを読み込む | **1**（MULTISET） | 2 | 2 |

※ `JdbcClient` には一括処理（バッチ）の API がないので、`NamedParameterJdbcTemplate.batchUpdate` を併用した。JDBC のバッチとしてまとめて送るので往復回数は少ないが、DB 側では1行ずつの文として実行される（PostgreSQL ドライバの `reWriteBatchedInserts=true` を使えば、複数行の INSERT 1本にまとめられる）。Spring Data JDBC の INSERT は1件ずつ別々に送られる。

### 観点: AI フレンドリーか

コードの大半を AI エージェントが書いて直すので、次の5つの観点で評価した。

| 観点 | jOOQ | Spring Data JDBC | JdbcClient |
|---|---|---|---|
| ① 最初から正しく書けるか（AI がよく知っているか） | ○ DSL はよく知られている。ただ API が広く、新しい機能（MULTISET、`excluded()`）では誤った書き方をしやすい | ○ API が小さい。ただ「割り当て済みIDは新規扱いされない」などの決まりごとを知らないとはまりやすい | ◎ SQL そのものなので最も書きやすい |
| ② 間違えたときのフィードバック | **◎ コンパイラが行番号と記号名を示す。Docker がなくても動く** | △ 実行時。DB が必要 | △ 実行時。DB が必要。エラーメッセージ（`column ... does not exist`）は分かりやすい |
| ③ 人がレビューするときの読みやすさ | ○ SQL に近いが、MULTISET の対応付けは密度が高い | ○ SQL が隠れる（ログを見ないと分からない） | ◎ 実際に流れる SQL がそのまま見える |
| ④ スキーマ変更の影響範囲を洗い出せるか | **◎ 生成をやり直すと、影響する箇所がすべてコンパイルエラーとして並ぶ。そのまま作業リストになる** | △ テストと grep 頼み | △ 文字列を grep するしかない |
| ⑤ AI が手順を守れないときのリスク | △ 「マイグレーションを変えたらコードを生成し直す」を忘れると、古いスキーマのままコンパイルが通る。生成コードを手で直してしまう恐れもある | ○ 特別な手順はない | ○ 特別な手順はない |

まとめると、JdbcClient は「**書くとき**」に、jOOQ は「**間違えたとき・変えるとき**」に AI フレンドリー。エージェントが自律的に開発を回すうえで効くのは後者だと判断した。最初の一回で正しく書けなくても、コンパイラがすぐ正しい方向へ導いてくれるからだ。jOOQ の弱点⑤は、仕組みで防げる（下記）。

### 見つかったこと（ライブラリに関係なく大事な点）

1. **RLS は「何も見せない」側に倒れるので、トランザクションの付け忘れが静かに隠れる。**
   - スパイク中に実際に起きた。ポートの default メソッド `getOrEmpty` には `@Transactional` が効かず、中から呼ぶ `findByMonth` も自己呼び出しでプロキシを通らなかった。
   - その結果、全アダプタで「保存したプランが GET で空になる」バグになった。リポジトリを直接呼ぶ契約テストでは見つからず、HTTP 経由のテストで見つかった。
   - 対策は3つ。
     - (a) ポートから default メソッドをなくした。
     - (b) `app_current_user_id()` は、ユーザーIDが設定されていなければ**例外を投げる**ようにした。黙って0件を返すのではなく、すぐ壊れる。
     - (c) HTTP 経由の結合テストを、アダプタごとに流すようにした。
2. **アプリのSQLは `user_id` に一切触れない。** 絞り込みは RLS と列の既定値に任せている。コードは簡潔になるが、**RLS の設定を誤るとすぐに情報漏えいにつながる**。そのため、RLS の契約テスト（別のユーザーから見えないこと、同じキーでも衝突しないこと）は削除・スキップしないこと。
3. **アプリは所有者ではないロール（`runbuddy_app`）で接続する。** Testcontainers の既定ユーザーはスーパーユーザーで RLS を素通りするので、テストでもアプリ用のロールを使う必要がある。

## 決定

**jOOQ を採用する。** 理由は次のとおり。

- AI が書いた誤りの多くをコンパイル時に見つけられる。Docker や DB がない環境でも検査が効く（計測1、観点②）。
- スキーマを変えたとき、影響する箇所をコンパイラが洗い出してくれる（観点④）。
- upsert や MULTISET など PostgreSQL の機能をそのまま使えて、SQLの本数が件数に依存しない（計測2）。
- RLS の扱いやすさは、3つのライブラリで変わらない（共通の `RlsTransactionManager`）。決め手にはならない。

JdbcClient は最も素直で書きやすい（観点①③）。ただ、「間違いにテストでしか気付けない」点が自律的なエージェント開発では弱いので、採用しない。複数の書き方を混在させない方が AI にとっても一貫性があるので、併用もしない。jOOQ で書きにくい SQL は、jOOQ の plain SQL API（`dsl.resultQuery("...")`）で書く。

### jOOQ の弱点（観点⑤）を防ぐ仕組み

- CI で `scripts/generate-jooq.sh` を実行し、**生成コードに差分が出たら失敗させる**。マイグレーションを変えたのにコードを生成し直していない状態を検出するため。
- `backend/CLAUDE.md` に次を明記する。
  - 生成コードを手で編集しない。
  - マイグレーションを変更したらコードを生成し直す。
  - DB アクセスはトランザクションの中で行う。

承認後に次を行った。

- Spring Data JDBC 版と JdbcClient 版のアダプタ、および不要になった依存を削除した。比較に使ったコードは git の履歴（コミット `a8ff5d6`）に残っている。
- `runbuddy.persistence` の選択肢を `jooq` と `memory` だけにした。
- 上の仕組み（CI の定義と `backend/CLAUDE.md`）を入れた。CI の定義は `.github/workflows/ci.yml`（Claude の GitHub App にはワークフローファイルを push する権限がないため、配置はオーナーが行った）。
