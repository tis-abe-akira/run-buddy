# ADR-0007: 永続化ライブラリの選定（PostgreSQL + RLS）

- ステータス: **Proposed**（オーナーの判断待ち。上位2候補でスパイクしてから決める）
- 日付: 2026-10-31

## コンテキスト

Phase 1 のデータはメモリ上にしかない（`InMemoryMonthlyPlanRepository`、`InMemoryRunResultRepository`）。
これを PostgreSQL に保存するようにする。将来は Row Level Security（RLS）で、ユーザーごとにデータを分けたい。

ライブラリを選ぶうえで、このプロジェクトならではの前提は次の4つ。

1. **ドメインモデルはイミュータブルな record で、不変条件をコンストラクタで守っている**（`MonthlyPlan`、`RunResult`、値オブジェクトの `Distance`）。永続化のためにドメインを書き換える（可変にする、引数なしコンストラクタを足す）ことは避けたい。
2. **リポジトリはすでにポートになっている**（ADR-0004）。どのライブラリを選んでも、変わるのはアダプタだけ。
3. **PostgreSQL 特有の機能を使う**: RLS（`set_config` でセッション変数を設定）、`INSERT ... ON CONFLICT`（取り込みを何度実行しても重複させないため）。
4. **コードの多くを AI エージェントが書く**: SQL やマッピングの誤りを、実行時ではなくコンパイル時に見つけられる方が安全。

### RLS をアプリから使う方法（どのライブラリでも共通）

- トランザクションの最初に `select set_config('app.user_id', ?, true)` を実行する（第3引数が `true` なので、トランザクションが終われば消える。コネクションプールで別のリクエストに値が残らない）。
- アプリは**テーブルの所有者ではないロール**で接続する（所有者は RLS を素通りするため）。マイグレーション（Flyway）は所有者ロールで実行する。
- これは Spring のトランザクション管理に乗るどのライブラリでも、同じ仕組み（トランザクション開始時に呼ぶ小さな部品）で実装できる。違いが出るのは「ライブラリの裏で何が起きるか」が読みやすいかどうか。

### 各案を一言で

- **JPA**: エコシステムは最大。ただ、このプロジェクトの前提1（record のドメイン）と前提4（挙動の見通し）に合わず、ドメインと JPA エンティティの二重管理になる。RLS を「試す」目的にも、裏で発行されるSQLが見えにくい点が邪魔になる。
- **MyBatis**: SQLを完全に制御できて堅実。ただ、マッピングの誤りが実行時まで分からないので、AI が書くとテストでしか守れない。
- **Spring Data JDBC**: DDD の集約の考え方が `MonthlyPlan`（親）＋`PlannedWorkout`（子のリスト）にそのまま当てはまる。一方で、取り込みの upsert や集計クエリは生SQLを書くことになり、そこでは型安全性がない。
- **jOOQ**: PostgreSQL の機能と RLS の検証に一番素直。スキーマから生成したコードのおかげで、AI が書いたクエリの誤りをコンパイラが見つけられる。代わりにコード生成の仕組みが必要になる（下記）。
- **Doma**: 2-way SQL とコンパイル時検査のバランスが良い。ただ、利用者と情報が比較的少ない。

### jOOQ のコード生成について

コード生成には DB のスキーマが必要になる。方法は2つある。

- (a) ビルド中に Testcontainers で PostgreSQL を起動し、Flyway を流してからコードを生成する。本物の PostgreSQL のスキーマから作れる。
- (b) jOOQ の `DDLDatabase` で、Flyway のSQLファイルを解析して生成する。DB は要らないが、RLS のポリシー定義などは解析を除外する指定が必要になる。

この開発環境では Docker デーモンが動いていない（2026-10-31 時点）。ただし PostgreSQL 16 の実行ファイルはあるので、ローカルで起動した PostgreSQL を使う方法も取れる。

## 推奨

**第一候補は jOOQ、次点は Spring Data JDBC。** どちらにするかは、両方で小さく作ってみて（スパイク）から決める。

決め方の案は次のとおり。

1. Flyway で `monthly_plan` / `planned_workout` / `run_result` テーブルを作る。
2. **リポジトリの契約テスト**（抽象テストクラス）を書き、`InMemory` 実装・jOOQ 実装・Spring Data JDBC 実装の3つに同じテストを流す。
   - 例: 保存したものを読み戻せる / ワークアウトが日付順になる / 取り込みを何度実行しても重複しない
3. 比べる観点:
   - アダプタのコード量
   - upsert の書きやすさ
   - RLS（`set_config`）を入れたときに読みやすいか
   - AI エージェントが間違えたときに、どの段階で気付けるか（コンパイル時／起動時／テスト実行時）
4. 結果をこの ADR に追記し、Accepted にする。

JPA と MyBatis は、この表の時点で候補から外す（理由は上の「各案を一言で」）。

## 結果（トレードオフ）

- どれを選んでも、ドメインとサービスは変わらない（ポートを分けておいた効果）。
- jOOQ を選んだ場合は、ビルドとCIにコード生成の手順が増える。
- RLS は「アプリが所有者ではないロールで接続する」ことが前提なので、DB のロール設計（マイグレーション用とアプリ用）を別の ADR で決める。
