# ADR-0007: 永続化ライブラリの選定（PostgreSQL + RLS）

- ステータス: **Proposed**（スパイク完了。推奨は jOOQ。オーナーの承認待ち）
- 日付: 2026-10-31

## コンテキスト

Phase 1 のデータはメモリ上にしかない（`InMemoryMonthlyPlanRepository`、`InMemoryRunResultRepository`）。
これを PostgreSQL に保存するようにする。将来は Row Level Security（RLS）で、ユーザーごとにデータを分けたい。

ライブラリを選ぶうえで、このプロジェクトならではの前提は次の4つ。

1. **ドメインモデルはイミュータブルな record で、不変条件をコンストラクタで守っている**（`MonthlyPlan`、`RunResult`、値オブジェクトの `Distance`）。永続化のためにドメインを書き換える（可変にする、引数なしコンストラクタを足す）ことは避けたい。
2. **リポジトリはすでにポートになっている**（ADR-0004）。どのライブラリを選んでも、変わるのはアダプタだけ。
3. **PostgreSQL 特有の機能を使う**: RLS（`set_config` でセッション変数を設定）、`INSERT ... ON CONFLICT`（取り込みを何度実行しても重複させないため）。
4. **コードの多くを AI エージェントが書く**: SQL やマッピングの誤りを、実行時ではなくコンパイル時に見つけられる方が安全。

### RLS をアプリから使う方法（どのライブラリでも共通）

- トランザクションの最初に `select set_config('app.user_id', ?, true)` を実行する（第3引数が `true` なので、トランザクションが終われば消える。コネクションプールで別のリクエストに値が残らない）。
- アプリは**テーブルの所有者ではないロール**で接続する（所有者は RLS を素通りするため）。マイグレーション（Flyway）は所有者ロールで実行する。
- これは Spring のトランザクション管理に乗るどのライブラリでも、同じ仕組み（トランザクション開始時に呼ぶ小さな部品）で実装できる。違いが出るのは「ライブラリの裏で何が起きるか」が読みやすいかどうか。

### 各案を一言で

- **JPA**: エコシステムは最大。ただ、このプロジェクトの前提1（record のドメイン）と前提4（挙動の見通し）に合わず、ドメインと JPA エンティティの二重管理になる。RLS を「試す」目的にも、裏で発行されるSQLが見えにくい点が邪魔になる。
- **MyBatis**: SQLを完全に制御できて堅実。ただ、マッピングの誤りが実行時まで分からないので、AI が書くとテストでしか守れない。
- **Spring Data JDBC**: DDD の集約の考え方が `MonthlyPlan`（親）＋`PlannedWorkout`（子のリスト）にそのまま当てはまる。一方で、取り込みの upsert や集計クエリは生SQLを書くことになり、そこでは型安全性がない。
- **jOOQ**: PostgreSQL の機能と RLS の検証に一番素直。スキーマから生成したコードのおかげで、AI が書いたクエリの誤りをコンパイラが見つけられる。代わりにコード生成の仕組みが必要になる（下記）。
- **Doma**: 2-way SQL とコンパイル時検査のバランスが良い。ただ、利用者と情報が比較的少ない。

### jOOQ のコード生成について

コード生成には DB のスキーマが必要になる。方法は2つある。

- (a) ビルド中に Testcontainers で PostgreSQL を起動し、Flyway を流してからコードを生成する。本物の PostgreSQL のスキーマから作れる。
- (b) jOOQ の `DDLDatabase` で、Flyway のSQLファイルを解析して生成する。DB は要らないが、RLS のポリシー定義などは解析を除外する指定が必要になる。

スパイクでは、(a) の考え方をスクリプトで実現した（`backend/scripts/generate-jooq.sh`）。スクリプトが使い捨ての PostgreSQL コンテナを起動し、Flyway と jOOQ のコード生成を流す。生成したコードはコミットするので、通常のビルドに Docker は要らない。`testcontainers-jooq-codegen-maven-plugin` も検討したが、0.0.4 と古く、Boot 4 が管理するバージョンとの互換性が不安なので見送った。

## 推奨

**第一候補は jOOQ、次点は Spring Data JDBC。** どちらにするかは、両方で小さく作ってみて（スパイク）から決める。

決め方の案は次のとおり。

1. Flyway で `monthly_plan` / `planned_workout` / `run_result` テーブルを作る。
2. **リポジトリの契約テスト**（抽象テストクラス）を書き、`InMemory` 実装・jOOQ 実装・Spring Data JDBC 実装の3つに同じテストを流す。
   - 例: 保存したものを読み戻せる / ワークアウトが日付順になる / 取り込みを何度実行しても重複しない
3. 比べる観点:
   - アダプタのコード量
   - upsert の書きやすさ
   - RLS（`set_config`）を入れたときに読みやすいか
   - AI エージェントが間違えたときに、どの段階で気付けるか（コンパイル時／起動時／テスト実行時）
4. 結果をこの ADR に追記し、Accepted にする。

JPA と MyBatis は、この表の時点で候補から外す（理由は上の「各案を一言で」）。

## 結果（トレードオフ）

- どれを選んでも、ドメインとサービスは変わらない（ポートを分けておいた効果）。
- jOOQ を選んだ場合は、ビルドとCIにコード生成の手順が増える。
- RLS は「アプリが所有者ではないロールで接続する」ことが前提なので、DB のロール設計（マイグレーション用とアプリ用）を別の ADR で決める。

## スパイクの結果（2026-10-31）

### 作ったもの

- **スキーマ:** Flyway の `V1__create_plans_and_runs.sql`。RLS のポリシー、`user_id` 列の既定値、関数 `app_current_user_id()` を含む。
- **アダプタ:** jOOQ 版（`persistence/jooq`）と Spring Data JDBC 版（`persistence/jdbc`）。`runbuddy.persistence=jooq|jdbc|memory` で切り替える。
- **RLS の仕組み:** `RlsTransactionManager` がトランザクションの開始時に `set_config('app.user_id', ?, true)` を実行する。2つのライブラリで共通（24行）。
- **契約テスト:** プラン5件・ラン7件・RLS 2件・HTTP 経由の結合テスト2件。InMemory / jOOQ / Spring Data JDBC の各実装に同じテストを流し、**すべて通った**。DB を使うテストは Testcontainers（PostgreSQL 17）で、本番と同じく所有者ではないロールで接続する。テストごとに新しいユーザーとして実行するので、後片付けは要らない。

### 計測 1: 間違いにどの段階で気付けるか

コードにわざと誤りを入れて確かめた。

| 入れた誤り | jOOQ | Spring Data JDBC |
|---|---|---|
| カラム名の打ち間違い | **コンパイルエラー** | コンパイルは通る → テスト時に9件エラー（`column does not exist`） |
| 型の違う値の並び順を取り違える | **コンパイルエラー**（`no suitable method found for values(...)`） | 該当しない（コンストラクタの引数を名前で対応付ける） |
| 同じ型（long 同士）の値を入れ替える | テストで検出（4件失敗） | テストで検出（4件失敗） |
| スキーマを変えたのにコードを直し忘れる | コード生成をやり直すとコンパイルエラーになる | テストを実行するまで分からない |

### 計測 2: 発行されるSQLの本数

PostgreSQL の `log_statement=all` で数えた。BEGIN / COMMIT / set_config は除く。

| 操作 | jOOQ | Spring Data JDBC |
|---|---|---|
| 24件のランを取り込む（新規） | **2** | 25 |
| 同じ24件を再度取り込む | **2** | 25 |
| 22件のワークアウトを含むプランを保存（新規） | **3** | 24 |
| 同じプランを再度保存 | **3** | 25 |
| プランを読み込む | **1**（MULTISET で親と子をまとめて取得） | 2 |

Spring Data JDBC は upsert ができず、子要素の INSERT も1件ずつになるので、SQLの本数が件数に比例して増える。

### 計測 3: コード量（空行・コメント・import を除く）

| | 手書き | 生成 |
|---|---|---|
| jOOQ | 134行 / 3ファイル | 1,484行 / 11ファイル（コミットする） |
| Spring Data JDBC | 116行 / 5ファイル（永続化用の Row record を含む） | なし |

### 見つかったこと（ライブラリに関係なく大事な点）

1. **RLS は「何も見せない」側に倒れるので、トランザクションの付け忘れが静かに隠れる。**
   - スパイク中に実際に起きた。ポートの default メソッド `getOrEmpty` には `@Transactional` が効かず、中から呼ぶ `findByMonth` も自己呼び出しでプロキシを通らなかった。
   - その結果、両方のアダプタで「保存したプランが GET で空になる」バグになった。リポジトリを直接呼ぶ契約テストでは見つからず、HTTP 経由のテストで見つかった。
   - 対策は3つ。
     - (a) ポートから default メソッドをなくした。
     - (b) `app_current_user_id()` は、ユーザーIDが設定されていなければ**例外を投げる**ようにした。黙って0件を返すのではなく、すぐ壊れる。
     - (c) HTTP 経由の結合テストを、アダプタごとに流すようにした。
2. **アプリのSQLは `user_id` に一切触れない。** 絞り込みは RLS と列の既定値に任せている。コードは簡潔になるが、**RLS の設定を誤るとすぐに情報漏えいにつながる**。そのため、RLS の契約テスト（別のユーザーから見えないこと、同じキーでも衝突しないこと）は削除・スキップしないこと。
3. **アプリは所有者ではないロール（`runbuddy_app`）で接続する。** Testcontainers の既定ユーザーはスーパーユーザーで RLS を素通りするので、テストでもアプリ用のロールを使う必要がある。

## 結論（案）

**jOOQ を採用する。** 理由は次のとおり。

- AI が書いた誤りの多くをコンパイル時に見つけられる（計測1）。
- upsert や MULTISET など PostgreSQL の機能をそのまま使えて、SQLの本数が件数に依存しない（計測2）。
- RLS の扱いやすさは2つのライブラリで変わらない（共通の `RlsTransactionManager`）。決め手にはならない。

Spring Data JDBC の長所（コード生成が要らない、集約の考え方が素直）も確認できた。ただ、上の2点を上回るほどではなかった。

承認されたら、次を行う。

- Spring Data JDBC 版のアダプタと依存を削除する。
- `runbuddy.persistence` の選択肢を `jooq` と `memory` だけにする。
- この ADR を Accepted にする。
