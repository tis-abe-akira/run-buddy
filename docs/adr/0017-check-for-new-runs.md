# ADR-0017: 新しいランは画面が定期的に確かめ、ヘッダーの通知から取り込む

- ステータス: Accepted
- 日付: 2026-11-19
- 関連: #40、ADR-0009（Garmin、レート制限は不明）、ADR-0016（取り込み時の一言）

## コンテキスト

走ったあと、ダッシュボードを少しスクロールして「最新を取り込む」ボタンを探して押していた。使えないわけではないが、
アプリを開いたらすぐ目に入る場所で「新しいランがある」と分かり、押せば取り込まれる方がよい（#40）。

一方で、Garmin の Personal API のレート制限の値は分かっていない（ADR-0009）。確かめる回数は抑えたい。

## 決定

1. **確かめるだけの API** `GET /api/runs/latest/check` を足す。`RunImportService.findNewRuns()` が「最新を取り込む」と同じ範囲
   （保存済みの最新のランの前日〜今日）を取り込み元から読み、保存済みでないランだけを返す。保存も `RunsImported` の通知もしない。
2. **確かめる間隔は backend の設定** `runbuddy.activity.check-interval`（既定 3 分）。API は間隔を `checkIntervalSeconds` で返し、
   画面はその間隔で次を確かめる。間隔の設定を 1 か所にするため、画面に数値を持たない。
3. **取り込み元に問い合わせるのは、間隔ごとに 1 回まで。** `NewRunChecker` が答え（と失敗）を間隔のあいだ覚えておき、
   PC とスマホなど複数の画面から確かめても共有する。確かめている最中の呼び出しは、それを待つ。
   取り込みがあれば（`RunsImported`）覚えた答えを捨て、取り込んだばかりのランを再び「新しい」とは言わない。
4. **画面が見えているときだけ確かめる。** TanStack Query の `refetchInterval`（裏のタブでは止まる）と、画面に戻ったときの 1 回。
   失敗（429・キー切れ・ネットワーク）のあとは間隔を 4 倍にする。確かめる処理の失敗は通知に出さない（ダッシュボードのボタンで取り込めば理由が出る）。
5. **通知はヘッダーの右端**（スマホではナビの下の行）。どのページにも出る。1 件なら「11/19 のランを取り込む」、複数なら件数。
   押すと「最新を取り込む」と同じ取り込みを行い、**取り込んだ一番新しいランの日のページへ移る**（評価・地図・ラップがそこにある）。
   取り込み結果 `LatestImportResult` に、取り込んだラン `newRuns` を足した。
6. 今の「最新を取り込む」「○月を取り込み直す」は残す。

## 検討した選択肢

| 案 | 判断 |
|---|---|
| **画面が定期的に確かめ、押したら取り込む**（採用） | 取り込むかどうかはランナーが決める。オーナーの要望どおり |
| 確かめたら自動で取り込む | 取り込みは AI の一言（ADR-0016）も動かしうる。押して取り込む方が分かりやすい、というオーナーの判断 |
| backend が定期的に確かめ、画面に push（SSE など） | 画面を開いていないあいだも Garmin に問い合わせ続ける。今の規模ではポーリングで足りる |
| OS（ブラウザ）の通知 | 許可やバックグラウンド処理が要る。必要なら別の Issue |

## 結果（トレードオフ）

- 良い点：開けば目に入り、押せばその日のページに着く。Garmin への問い合わせは画面の数によらず、間隔ごとに 1 回まで。
- 注意点：覚えておく答えは backend のメモリにあり、再起動で消える（最初の確認で問い合わせ直すだけ）。ユーザーが一人である前提（`CurrentUser`）。
  サインインを入れて複数のユーザーにするときは、答えをユーザーごとに分ける必要がある。
- 注意点：取り込み元で新しいランが増えてから、通知が出るまで最大でおよそ 1 間隔（既定 3 分）かかる。
