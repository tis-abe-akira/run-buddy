# ADR-0008: AI相談機能（Phase 2）の実装方式

- ステータス: Accepted（2026-10-31。Spring AI を採用。プロバイダとモデルは相談のたびに選ぶ。最初のプロバイダは Gemini）
- 日付: 2026-10-31
- 改訂: 同日、「LLM を **Gemini / Claude / OpenAI / Amazon Bedrock** から選べるようにする」という要件が加わったため、比較をやり直した（初版は Claude だけを前提にしていた）

## コンテキスト

Phase 2 では「トレーニング計画を AI に相談する」機能を作る（concept.md UC-4）。想定している動きは次のとおり。

- ユーザーが「来月のプランを相談したい」「今月の走りはどうだった？」と話しかけると、AI が実績と計画を見て答える。
- AI が、必要なデータ（月ごとの実績、計画、達成状況）を**自分で取りに行く**（ツール呼び出し）。
- AI が**次の月のプラン案を構造化データで返す**。ユーザーが採用すると、`MonthlyPlan` として保存される。
- やりとりは会話として続けられる（複数ターン）。
- **使う LLM を Gemini（Google）/ Claude（Anthropic）/ GPT（OpenAI）/ Amazon Bedrock から選べる。**

すでに決まっている前提は次のとおり。

1. データは PostgreSQL の行レベルセキュリティ（RLS）で守っている。DB アクセスは `RlsTransactionManager` を通る Java 側にしかない（ADR-0007）。
2. 外部サービスとの連携はポートで分ける。AI もポート `TrainingAdvisor` として扱う（ADR-0004）。
3. プラン案は、ドメインの不変条件を守る `MonthlyPlan` を通してから保存する。
4. コードの多くを AI エージェントが書く。そのため、型による検査と速いフィードバックを重視する（ADR-0007）。

### 「Bedrock」について

Bedrock は LLM の会社ではなく、**AWS 上で複数の会社のモデル（Claude、Llama、Amazon Nova など）を同じ API（Converse API）で使えるプラットフォーム**。そのため「Claude」は、Anthropic の API から直接使う方法と、Bedrock 経由で使う方法の2通りがある。Bedrock 経由の利点は、AWS の認証（IAM）、請求、リージョンの指定（データをどの地域で処理するか）にそろえられること。

## 検討した選択肢

| 案 | 内容 |
|---|---|
| A. **Spring AI** | Spring の公式プロジェクト。`ChatClient` / `ChatModel` で、各社の違いを吸収する |
| B. **LangChain4j** | Java 版 LangChain。各社に対応し、Spring Boot の starter もある |
| C. 各社の公式 Java SDK を自分で包む | 4社の SDK の上に、自前の抽象化を作る |
| D. **Python（FastAPI）+ LiteLLM / LangChain** | AI 部分を別サービスにし、backend から HTTP で呼ぶ |

確認日: 2026-10-31（Maven Central）

- Spring AI 2.0.2 には `spring-ai-anthropic` / `spring-ai-openai` / `spring-ai-google-genai`（Gemini）/ `spring-ai-bedrock-converse` があり、starter も anthropic / openai / google-genai / bedrock がある。Bedrock Converse 用 starter の正確な名前は、スパイクで確認する。
- Spring AI の Anthropic 用モジュールは、公式 Java SDK の 2.72.0（最新は 3.3.0）に依存している。抽象化を挟むぶん、各社の新しい機能への対応は遅れがちになる。

| 観点 | A. Spring AI | B. LangChain4j | C. 自前で包む | D. Python |
|---|---|---|---|---|
| 4社の切り替え | ◎ | ◎ | △ 4社分の違い（ツール呼び出し、構造化出力、ストリーミング、エラー）を自分で吸収する。抽象化をもう1つ作るのと同じ | ◎ LiteLLM などで吸収できる |
| ツールから RLS 付きのデータを読む | ◎ `@Tool` を付けたメソッドから、リポジトリを直接呼べる | ◎ `@Tool` で同様にできる | ◎ | △ Java の API を呼び返す必要がある。ユーザーの認証情報の受け渡しが要り、RLS の境界が2つのサービスにまたがる |
| プラン案を `MonthlyPlan` で検証する | ◎ `entity(Record.class)` で record に変換できる | ◎ AiServices の戻り値の型で受け取れる | ○ | △ 型を Python と Java の二重に持つことになる |
| Spring Boot 4 との統合（自動設定、設定プロパティ、観測性） | ◎ Spring の公式プロジェクト。Micrometer による観測性も標準で付く | ○ starter はあるが、Spring の外のプロジェクト | — | — |
| 各社の固有機能（Claude の思考の深さ、プロンプトキャッシュなど） | ○ 各社ごとの Options クラスで指定する。対応は遅れがち | ○ 同程度 | ◎ | ○ |
| AI フレンドリー | ○ 型あり。ただ 2.0 は新しく、AI が 1.x の古い書き方をしがち | ○ 型あり。バージョンによる API の変化は同程度 | ○ | △ 言語が2つ |
| 運用 | 1プロセス | 1プロセス | 1プロセス | 2サービス |

### 判断

- **C（自前で包む）は採らない。** 4社の差を自分で吸収するのは、A や B がすでにやっていることの作り直しになる。
- **D（Python）は採らない。** 理由は初版と同じ。データ・権限（RLS）・ドメインの不変条件が Java 側にあり、サービス境界越しに受け渡すコストが大きい。複数社に対応できるという利点は、A と B にもある。
- **A と B は機能的にはほぼ互角。** このプロジェクトでは **A（Spring AI）** を選ぶ。理由は次のとおり。
  - Spring Boot 4 の公式な仲間なので、設定プロパティ・自動設定・観測性（Micrometer）・テストの作法が、既存の backend とそろう。
  - オーナーが Spring のエコシステムに寄せる方針を持っている。
  - B は、A に致命的な不具合や機能不足が見つかったときの代わりにする。

## 推奨: Spring AI を採用し、4社で動くことをスパイクで確かめる

### 設計方針

1. **ポート `TrainingAdvisor` はプロバイダに依存しない。** Spring AI の型もポートの外には出さない。
   - 例: `Advice consult(Conversation conversation, AdvisorChoice choice)`。`Advice` には返答の文章と、あればプラン案（`MonthlyPlan`）を含める。
2. **4社が共通して持っている機能だけで、機能の中心を作る。** つまり、チャット、ツール呼び出し、構造化出力。
   - 各社の固有機能（Claude の思考の深さ、プロンプトキャッシュなど）は、アダプタの設定で「あれば使う」扱いにとどめる。それがないと機能が成り立たない作りにはしない。
3. **構造化出力はモデルによって信頼度が違う。** 返ってきたプラン案は必ず `MonthlyPlan` の不変条件で検証する。失敗したら、エラーの内容を添えて一度だけ作り直しを頼む。それでも駄目なら、文章だけの返答にする。
4. **ツールは短いトランザクションで動かす。** LLM の呼び出しは DB トランザクションの外で行う（応答に数十秒かかることがあるため）。
5. **AI のプラン案は自動では保存しない。** ユーザーが採用したときだけ、既存の `PUT /api/plans/{month}` の経路で保存する。
6. **認証情報は環境変数で渡す。** API キーや AWS の認証情報（IAM）が設定されたプロバイダだけを選べるようにする。キーはリポジトリに置かない。

### プロバイダを選ぶ単位（オーナーの判断が必要）

| 方式 | 内容 | 向いている場面 |
|---|---|---|
| (1) 環境ごとの設定 | `runbuddy.ai.provider=gemini` のように、デプロイ時に1つ選ぶ | 運用者が決めればよい場合。もっとも単純 |
| (2) リクエストごと | 画面でユーザーが「Claude に聞く / Gemini に聞く」を選ぶ。有効な ChatModel を複数用意し、名前で振り分ける | 比べながら使いたい場合、ユーザーが好みで選びたい場合 |

(2) を選んでも、(1) の設定で既定のプロバイダを決められるようにする。

### スパイクで確かめること

- Spring AI 2.0.x が Spring Boot 4.1 / Java 25 で動くこと。
- 4社の starter を同時に入れたときの自動設定の扱い。複数の ChatModel を作り、使うものを切り替えられるか。
- 4社すべてで、次の3つが動くこと。
  - ツール呼び出しで RLS 付きのデータを読める（ツールが別スレッドで実行されても `CurrentUser` が引き継がれるか。引き継がれない場合は、`app_current_user_id()` がすぐエラーにするはず）
  - 構造化出力を `MonthlyPlan` に変換できる
  - 複数ターンの会話ができる
- 各社の固有機能を Options でどこまで指定できるか（例: Claude の adaptive thinking と effort）。
- 拒否・上限到達・レート制限（429）などのエラーが、各社でどう現れるか。そして、それを共通のエラーに変換できるか。

### テストの方針

- **LLM を呼ばないテスト:** 偽物の `TrainingAdvisor` で、ドメイン・API・画面をテストする。CI で毎回流す。
- **録画テスト（プロバイダごとの契約テスト）:** 各社との実際のやりとりを記録して再生し、アダプタが正しく変換することを確かめる。CI で毎回流す。
- **実際に各社を呼ぶテスト:** 手動、または定期的に流す。4社分の費用がかかるので、毎回は流さない。
- **評価（eval）:** 同じ相談を4社に投げ、返答の質を比べる。各社の得意・不得意を知る材料にもなる。

### データの取り扱い

心拍数などの健康に関わるデータを、選んだ会社の API に送ることになる。

- どの会社に送るのかを画面で分かるようにする。
- Bedrock は AWS のリージョンを選べる。データを処理する地域の要件が出たら、Bedrock を既定にすることも考える。

## 結果（トレードオフ）

- Java 内で完結させるので、データ・権限・ドメインの境界は1か所のまま保たれる。
- 各社の新しい機能は、Spring AI が対応するまで使いにくい。機能の中心を共通の機能だけで作ることで、この影響を小さくする。
- ポート `TrainingAdvisor` があるので、Spring AI から LangChain4j や Python サービスへ乗り換えることになっても、ドメインと画面は変わらない。

## 決定（2026-10-31）

- **Spring AI を採用する。**
- **プロバイダとモデルは、相談のたびにユーザーが選ぶ**（上の表の方式 (2)）。会話の履歴はサーバーに保存しない。毎回クライアントが履歴全体を送るので、途中でプロバイダやモデルを変えてもよい。
- **最初に対応するのは Gemini。** API キーがまだないため、次のように準備した。
  - **Gemini の設定:** `GeminiAdvisorConfig` は、`GEMINI_API_KEY` が設定されたときだけ有効になる。
  - **偽物のプロバイダ（fake）:** キーがなくても画面まで動かせるように、ルールベースの `FakeTrainingAdvisor` を用意した（`runbuddy.ai.fake.enabled`。本番では無効にする）。fake も本物と同じツール（`AdvisorTools`）でデータを読むので、RLS の経路まで確かめられる。
  - **実際の Gemini を呼ぶテスト:** `GeminiLiveTest` は `GEMINI_API_KEY` があるときだけ動く。Spring AI のツール呼び出しの往復と、Gemini の構造化出力の質は、このテストで初めて確かめられる。
- **Spring AI の starter は使わず、プロバイダごとに設定クラスを手で書く。**
  - 理由: starter は API キーがないと起動に失敗するものがあり、複数のプロバイダの自動設定が衝突することもある。
  - 次のプロバイダ（Claude、OpenAI、Bedrock）は、同じ形の設定クラスを1つずつ足せばよい。
- **Spring AI 2.0.2 は Spring Boot 4.1 / Java 25 で問題なく動いた**（ビルドと、偽物の ChatModel を使ったテストで確認）。

## Gemini を実際に使った検証（2026-10-31）

AI Studio の API キー（無料枠）で、3か月分のダミー実績を相手に「先月の振り返り → 11月のプラン作成（週5回、日曜はロング走）」の会話を試した。

### モデルの比較

| モデル | 振り返り | プラン作成 | ツール呼び出し | 所見 |
|---|---|---|---|---|
| **gemini-2.5-flash** | 3〜8 秒 | 12〜22 秒 | 1〜3 回 | 速く安定している。分析はあっさりしている。**既定にした** |
| gemini-3.5-flash | 40 秒 | 89 秒 | 3〜4 回 | 日付や心拍数まで引用する、最も具体的な分析。じっくり相談したいとき用に選べるようにした |
| gemini-3.8-flash | 203 秒 | 5分以上で打ち切り | 5 回 | 内容は良いが、対話には遅すぎるので候補から外した |

3つとも、ツールで RLS 付きの実データを読み、`MonthlyPlan` の検証を通るプラン案を返した。Spring AI のツール呼び出しの往復と、Gemini の構造化出力は問題なく動いた。

### 見つかった問題と対策

1. **曜日の取り違え:** 2.5-flash が 2026-11-01（日）を土曜日として扱い、「日曜はロング走」を月曜に入れた（日曜にロング走が入ったのは 0/2）。
   - 対策: システムプロンプトに対象月のカレンダー（曜日ごとの日付）を入れ、ツールが返す日付にも曜日を付けた。
   - 結果: 修正後は日曜のロング走が 5/5 になった。
   - 学び: LLM に曜日を計算させない。
2. **達成率の誤り:** 実績 219.53 km ÷ 目標 220 km を、どのモデルも「達成率 100%」と書いた。原因はモデルではなくツール側で、整数に丸めて「100%」と渡していた。
   - 対策: 小数第1位まで渡すようにした（99.8%）。
   - 学び: モデルの誤りに見えるものが、渡しているデータの誤りであることがある。
3. **Markdown の混入:** 2.5-flash と 3.5-flash は `**太字**` を返し、画面に記号がそのまま表示された。
   - 対策: プロンプトで「Markdown を使わない」と指示した。
4. **利用上限（429）:** 無料枠には1分あたりのリクエスト数の上限があり、ツール呼び出しの1回ごとに1リクエストを消費する。短時間に試すと上限に当たった。
   - 対策: プロバイダごとの判定（Gemini は `ApiException.code() == 429`）で利用上限を見分け、HTTP 429 として「1分ほど待ってから送り直すか、別のモデルを選んでください」と画面に表示するようにした。
5. **失敗の原因がログに残らなかった。**
   - 対策: プロバイダの失敗を WARN で記録するようにした。

### 今後の検討

- 3.x 系の遅さは思考（thinking）に時間を使っているためと考えられる。`GoogleGenAiChatOptions` の `thinkingLevel` を下げれば速くなるかもしれない。設定は Gemini の設定クラスの `optionsForModel` に置ける。
- 本番で使う場合は、無料枠ではなく有料枠の利用上限を前提にする。
