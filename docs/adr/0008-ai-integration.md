# ADR-0008: AI相談機能（Phase 2）の実装方式

- ステータス: **Proposed**（オーナーの判断待ち。Java 内の2案でスパイクしてから決める）
- 日付: 2026-10-31

## コンテキスト

Phase 2 では「トレーニング計画を AI に相談する」機能を作る（concept.md UC-4）。想定している動きは次のとおり。

- ユーザーが「来月のプランを相談したい」「今月の走りはどうだった？」と話しかけると、AI が実績と計画を見て答える。
- AI が、必要なデータ（月ごとの実績、計画、達成状況）を**自分で取りに行く**（ツール呼び出し）。
- AI が**次の月のプラン案を構造化データで返す**。ユーザーが採用すると、そのまま `MonthlyPlan` として保存される。
- やりとりは会話として続けられる（複数ターン）。

この機能には、すでに決まっている前提がある。

1. データは PostgreSQL の行レベルセキュリティ（RLS）で守っており、DB アクセスは `RlsTransactionManager` を通る Java 側にしかない（ADR-0007）。
2. 外部サービスとの連携はポートで分ける。AI もポート `TrainingAdvisor` として扱うことが、ADR-0004 ですでに予告されている。
3. プラン案は、ドメインの不変条件（例: 月の外の日付は不可）を守る `MonthlyPlan` を通してから保存する。
4. コードの多くを AI エージェントが書く。そのため、型による検査と速いフィードバックを重視する（ADR-0007 の判断軸）。

LLM には Anthropic の Claude を使う。モデルは Claude Opus 5.5（`claude-opus-5-5`）を既定とする。コストのためにより安いモデルを使うかどうかは、実際の利用量を見てオーナーが判断する。

## 検討した選択肢

大きく分けて「Java の中で完結させる」か「Python のサービスを別に立てる」かの2つ。Java の中で完結させる案は、さらに「Spring AI を使う」か「公式 SDK を直接使う」かに分かれるので、合わせて3案を比べた。

- **A. Spring AI**: backend（Spring Boot）の中で Spring AI の `ChatClient` を使う。
- **B. Anthropic 公式 Java SDK を直接使う**: backend の中で `com.anthropic:anthropic-java` を使う。
- **C. Python（FastAPI）の AI サービスを別に立てる**: backend から HTTP で呼ぶ。中では公式 Python SDK（必要なら LangGraph など）を使う。

確認日: 2026-10-31（Maven Central）

- Spring AI の最新の正式版は 2.0.2。
- 公式 Java SDK の最新は 3.3.0。
- **Spring AI 2.0.2 の Anthropic 用モジュールは、公式 SDK の 2.72.0（メジャーバージョンが1つ古い）に依存している。**

| 観点 | A. Spring AI | B. 公式 Java SDK | C. Python（FastAPI） |
|---|---|---|---|
| ツールから RLS 付きのデータを読む | ◎ ツールはリポジトリを直接呼べる（同じプロセス、同じ `RlsTransactionManager`） | ◎ 同左 | △ Python から Java の API を呼び返す必要がある。ユーザーの認証情報を受け渡す仕組みが要り、RLS の境界が2つのサービスにまたがる |
| プラン案を `MonthlyPlan` として検証する | ◎ 構造化出力を record に変換して、そのままドメインに渡せる | ◎ 構造化出力（`output_config.format`）を record に対応付けられる | △ Python で検証した後、Java でもう一度ドメインの検証が要る。型を二重に定義することになる |
| Claude の最新機能（adaptive thinking と effort、拒否時のフォールバック、プロンプトキャッシュ、構造化出力など） | △ 抽象化のぶん遅れる（中の SDK がメジャーバージョン1つ古い）。使えない機能は、ネイティブクライアントに直接触れる形で補う必要がある | ◎ 公式 SDK なので最初に対応する | ◎ 公式 Python SDK は最初に対応する |
| LLM プロバイダの切り替え | ◎ 抽象化がある | ✕ Claude 専用 | ○ 書き方しだい |
| 書く量 | ◎ `@Tool` を付けたメソッド、`entity(Record.class)`、会話メモリの仕組みなどがそろっている | ○ ツール実行のループは SDK の Tool Runner（beta）に任せられる。会話の保存などは自分で書く | ○ Python 側は少ない。ただ、Java 側の API・認証・契約が増える |
| AI フレンドリー（型・フィードバック） | ○ 型あり。ただ 2.0 は新しく、AI が 1.x の古い書き方をしがち（Boot 4 と同じ問題） | ◎ 型あり。SDK の builder の誤りはコンパイルエラーになる | △ 言語が2つになる。型の共有は OpenAPI 経由で、ずれはテスト時まで分からない |
| テスト | ポート `TrainingAdvisor` を偽物に差し替えれば、LLM なしでドメインと画面をテストできる（A と B は同じ） | 同左 | Java 側は同左。Python 側にも別にテスト基盤が要る |
| 運用 | 1プロセス | 1プロセス | 2サービス（デプロイ、監視、CI、依存の更新がそれぞれ2倍） |
| Python のエコシステム（データ分析、機械学習、評価用ノートブック） | ✕ | ✕ | ◎ |

### 「AI なら Python」は今回当てはまるか

Python が強いのは、**モデルを自分で学習・推論する**場合や、pandas などで**データ分析が重い**場合だ。run-buddy の Phase 2 は「LLM の API を呼び、ツールで自分たちのデータを渡す」アプリなので、どの言語でも同じ API を呼ぶだけになる。一方で、データ・権限（RLS）・ドメインの不変条件はすべて Java 側にある。Python に分けると、それらをサービスの境界越しに受け渡すコストが、得られるものを上回る。

ただし、次のような必要が出てきたら C を改めて検討する。その場合も、ポート `TrainingAdvisor` の実装を「Python サービスを呼ぶ HTTP アダプタ」に差し替えれば済むので、今 Java を選んでも後で困らない。

- 練習負荷を自前のモデルで推定したい
- 大量の過去データを分析したい
- プロンプトを評価する基盤を Python で組みたい

## 推奨

**C（Python）は今回は採用しない。A（Spring AI）と B（公式 SDK を直接使う）を、ポート `TrainingAdvisor` の裏でスパイクして決める。** 現時点の見立ては **B がやや有利**。理由は次のとおり。

- Claude 専用なので、プロバイダを切り替えられることの価値が小さい。
- 抽象化が SDK の新機能に遅れる（中の SDK がメジャーバージョン1つ古い）ことを確認した。
- 「本物に近く、型で守る」という点で ADR-0007（jOOQ）と方針がそろう。

ただし、A の「書く量が少ない」利点が大きければ逆転しうる。

### スパイクの進め方（案）

ADR-0007 と同じく、同じポートと同じテストで A と B を比べる。

1. **ポート** `TrainingAdvisor` を定義する。
   - 例: `Advice consult(Conversation conversation)`。`Advice` には返答の文章と、あればプラン案（`MonthlyPlan`）を含める。
2. **ツール**（AI が呼べる関数）を3つ用意する。どれもリポジトリを通るので RLS が効く。
   - `get_month_summary(month)`
   - `get_runs(month)`
   - `get_plan(month)`
3. **契約テスト**を書く。
   - **LLM を呼ばないテスト:** 偽物の `TrainingAdvisor` を使い、ドメインと API をテストする。
   - **録画テスト（アダプタの契約テスト）:** 実際のやりとりを記録して再生する。ツール呼び出しが正しくリポジトリに届くこと、プラン案が `MonthlyPlan` の不変条件を通ることを確かめる。
   - **評価（eval）:** 返答の質は、少数の実例で別途評価する（CI では毎回は流さない。費用がかかるため）。
4. **比べる観点**
   - コード量
   - Claude の機能（adaptive thinking と effort、構造化出力、拒否時のフォールバック、プロンプトキャッシュ）をどこまで素直に使えるか
   - ツール実行時の RLS とユーザー文脈の受け渡し（ツールが別スレッドで動くと `CurrentUser` が失われないか。失われたら、`app_current_user_id()` がすぐエラーにするはず）
   - AI エージェントが間違えたときに、どの段階で気付けるか
   - Spring AI 2.0 と Spring Boot 4.1 の相性

### 設計上の注意（どの案でも共通）

- **LLM の呼び出しを DB のトランザクションの中で行わない。** 応答に数十秒かかることがあり、その間 DB 接続を握り続けてしまう。ツールはそれぞれ短いトランザクションで動かす。
- **AI のプラン案は、自動では保存しない。** ユーザーが採用したときだけ、既存の `PUT /api/plans/{month}` の経路で保存する。ドメインの検証と RLS をそのまま通すため。
- 心拍数などの健康に関わるデータを外部の API に送ることになる。利用者に分かるように画面で示す（Phase 2 の画面設計で扱う）。
- 拒否（`stop_reason: refusal`）や上限到達（`max_tokens`）を、画面で扱えるエラーとして返す。

## 結果（トレードオフ）

- Java 内で完結させるので、データ・権限・ドメインの境界は1か所のまま保たれる。
- Python のエコシステムは今は使わない。必要になれば、ポートの裏に Python サービスを置く形で後から足せる。
- A と B のどちらを選んでもポートの内側は変わらないので、後から乗り換えられる（ADR-0007 と同じ構図）。
