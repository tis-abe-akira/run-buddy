# ADR-0012: ラップと GPS 軌跡は FIT ファイルから取り、原本を DB に保存して、開いたときに読む

- ステータス: Accepted
- 日付: 2026-11-02
- 関連: #13（FIT の遅延読み込み）、#14（地図）、ADR-0004、ADR-0007、ADR-0009

## コンテキスト

日別詳細ページ（`/days/{日付}`）で、ランごとのラップを見たい。#14 では GPS の軌跡を地図に描きたい。

ADR-0009 の調査（2026-10-31、Swagger と実際の API）で分かったこと：

- **ラップ1本ずつのデータと GPS の軌跡は、Personal API の一覧・詳細の JSON には入っていない。**
  - 一覧（`/activitylist-service/activities/search/activities`）にあるのは `lapCount`（本数）だけ。
  - 詳細（`/activity-service/activity/{activityId}`）の `splitSummaries` は、実データでは空だった。一覧の `splitSummaries` は、インターバルの種類ごとの集計（`INTERVAL_ACTIVE` など）で、ラップ単位ではない。
  - 軌跡を返すエンドポイントはない。`hasPolyline` も全件 null だった。
- **FIT ファイル（`GET /download-service/files/activity/{activityId}`）には両方ある。**
  - レスポンスは `application/x-zip-compressed`。中に `.fit` が1つ入っている。実例で zip 約 100 KB、`.fit` 約 230 KB。
  - 実例1件で、`lap` メッセージが 26 本（一覧の `lapCount` と一致）。各ラップに距離・タイマー時間・平均/最大心拍・平均/最大ケイデンス・上昇/下降がある。
  - `record` メッセージ（記録点）が 1,836 点、そのうち 1,833 点に緯度経度。間隔は約 7 秒。心拍・ケイデンス・標高・速度も付いている。
  - FIT のケイデンスは**片足の回数/分**。両足の歩数/分にするには2倍し、`fractional_cadence` を足す。
- FIT は**1件ごとに1回のリクエスト**になる。レート制限の値は分かっていない（ADR-0009）。

## 決定

### 1. 遅延読み込み

- FIT は、ランの取り込み（一覧 API）のときには取らない。日別詳細ページで**そのランの詳細を初めて開いたとき**に1件だけ取る。
- 1回取ったら保存し、以後は Garmin を呼ばない。

### 2. 保存：FIT の原本（zip のまま）を PostgreSQL の新しいテーブルに置く

```sql
create table run_fit_file (
    user_id     text        not null default app_current_user_id(),
    activity_id text        not null,
    fit_zip     bytea       not null,
    fetched_at  timestamptz not null default now(),
    primary key (user_id, activity_id),
    foreign key (user_id, activity_id) references run_result (user_id, activity_id) on delete cascade
);
-- 他の表と同じく: enable/force row level security、own_rows ポリシー、runbuddy_app への権限
```

- 他のテーブルと同じ規則（`user_id`・既定値・`own_rows`・RLS）で守る。DB のバックアップにも含まれる。
- 容量の見積もり：1件約 100 KB、月 30 件で約 3 MB、年で約 36 MB。
- 同じランを2つのタブで同時に開いても、保存は `on conflict do nothing` で1件になる。

### 3. ラップや軌跡のテーブルは作らない。開くたびに原本から読む

- 原本が DB にあるので、ラップと軌跡は**表示のたびに FIT を解析して作る**。解析は1件数ミリ秒〜数十ミリ秒で、利用者は1人なので問題にならない。
- あとで別の項目（気温、パワー、ペースの推移など）を使いたくなっても、**マイグレーションも再ダウンロードも要らない**。
- 解析が重くなったら、そのときに結果をキャッシュするテーブルを足す（今はしない）。

### 4. ポートは取り込みとは別にする

- `activity` パッケージに、新しいポート **`ActivityFileSource`**：`Optional<byte[]> fetchFitZip(String activityId)`。
  - Garmin のアダプタは FIT をダウンロードする。失敗は `ActivitySourceUnavailableException`（理由つき、ADR-0009 と同じ）に変換する。
  - ダミーのアダプタは常に空を返す（ダミーのランには詳細がない）。
  - 取り込み用の `ActivitySource` とは呼ぶ頻度もコストも違い、ダミーでは用意できないので、分ける。
- 保存のポート **`RunFileRepository`**：保存と取得（契約テストを先に書く。jOOQ 版とメモリ版）。
- FIT の解析は `activity/fit` パッケージに閉じ込める。FIT SDK の型はこのパッケージの外に出さない。外に出すのはドメインの型だけ：
  - `RunDetail(List<Lap> laps, List<TrackPoint> track)`
  - `Lap`：開始時刻、距離、タイマー時間、平均/最大心拍、平均/最大ケイデンス（両足の歩数/分）、上昇。値の不変条件は `RunMetrics` と同じ考え方（正の値、最大 ≥ 平均）で、おかしな値はその値だけ捨てる。
  - `TrackPoint`：時刻、緯度、経度、（あれば）心拍・標高。#13 では保存と件数の表示まで。描画は #14。

### 5. API

- `GET /api/runs/{activityId}/detail`
  - 保存済みなら、原本を解析して返す。
  - 未保存なら、ダウンロード → 保存 → 解析 → 返す。
  - **ダウンロード中は DB のトランザクションを開かない**（AI の呼び出しと同じ規則、backend/CLAUDE.md）。「保存済みか調べる」「保存する」は、それぞれ短いトランザクションにする。
  - 返す内容：ラップの一覧と、軌跡の点の数（座標そのものは #14 で返す）。
  - ラン自体がない → 404。ダミーのラン（詳細なし）→ 200 で `available: false`。Garmin の失敗 → 今の取り込みと同じ ProblemDetail（`reason`：502 / 429）。

### 6. 画面

- 日別詳細ページのランごとに「ラップ」の欄を置く。概要（距離・心拍など）はすぐ表示し、ラップの欄だけ「読み込み中」にしてから表示する。
- 失敗したら、その欄にエラーと「再試行」を出す。概要はそのまま見られる。
- ダミーのランは「詳細データなし」と表示する。

### 7. FIT の読み込みには Garmin 公式の FIT SDK を使う

- `com.garmin:fit`（Maven Central、実行時の依存ライブラリなし）。
- ライセンスは Garmin 独自の「FIT Protocol License」で、オープンソースではない。自分のアプリで使うことは許されている。SDK 自体の再配布・公開は制限されている。
  - このリポジトリには SDK のソースを入れず、Maven の依存として参照するだけにする。
  - `-Papp` で作る jar には SDK が含まれる。この jar は自分のマシンで使うだけで、配布しない。

### 8. 位置情報とプライバシー

- GPS の軌跡からは、自宅などの場所が分かる。
- **今はスタート・ゴール付近を隠さない**（オーナーの判断、2026-11-02）。DB はオーナーの Mac mini にだけあり、見るのもオーナーだけ（ADR-0010）。表示するときにどうするかは、地図を描く #14 で改めて決める。
- **座標は AI 相談（Gemini）に送らない。** `AdvisorTools` は軌跡を返さない。
- テスト用の FIT は、FIT SDK のエンコーダで作った合成データにする。実在の位置・日時を含めない（リポジトリは public）。

## 検討した選択肢

| 案 | 判断 |
|---|---|
| A. 取り込みのときに FIT もまとめて取る | 月 30 件なら 30 回のダウンロード。レート制限が分からないので危ない。見ないランの分まで取る |
| **B. 開いたときに取り、原本を DB に保存し、毎回解析する**（採用） | リクエストは見たランの分だけ。項目を増やしてもマイグレーションが要らない |
| C. 開いたときに取り、ラップと軌跡をテーブルに分けて保存する（原本は捨てる） | 表示は少し速いが、項目を増やすたびにマイグレーションと再ダウンロードが要る。今の規模では速さの差に意味がない |
| D. 原本を Mac mini のフォルダに置く | RLS が効かない。DB とバックアップが別になる |
| E. 原本をクラウドのストレージ（S3 など）に置く | 個人のアプリには大げさで、データが外に出る |
| F. FIT を自前で解析する（SDK を使わない） | FIT の形式は複雑（開発者フィールド、圧縮タイムスタンプなど）。公式 SDK のほうが確実 |

## 結果（トレードオフ）

- 良い点：Garmin へのリクエストは、見たランにつき1回だけ。原本があるので、表示する項目を後から自由に増やせる。
- 良い点：ラップ・軌跡はドメインの型（`RunDetail`）として扱い、FIT SDK は `activity/fit` に閉じ込める。テストは合成 FIT で書ける。
- 注意点：初めて開くときは、ダウンロードの数秒を待つことになる。
- 注意点：Garmin Connect 側でランを編集しても、保存済みの FIT は古いまま。必要なら「詳細を取り直す」操作を後で足す（今はしない）。ランを削除すると（`on delete cascade`）、FIT も消える。
- 注意点：FIT SDK は Garmin 独自のライセンス。配布するアプリにするなら見直しが必要。

## 未確認

- 実装の途中で確かめた（2026-11-02、実際の API）：
  - **手入力のアクティビティも FIT をダウンロードできる**（200、zip 約 420 バイト）。中身はラップ 1 本だけで、記録点（軌跡）はない。読み込むと「ラップ 1 本、軌跡なし」になる。
  - **知らない ID は 404**。アダプタは「ファイルなし」として扱う。
  - `GarminLiveTest` で、最新のランの FIT をダウンロードして読み、ラップが取れることを確かめた。
- トレッドミル（GPS なし）のランは、期間内に実例がなく未確認。読み込みでは「軌跡が空」になるはず。
- FIT のダウンロードにレート制限がかかるかは分からない。
